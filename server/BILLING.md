# Ручное подтверждение оплаты и продление

Тариф: **150 RUB за 30 суток** (не календарный месяц). Комиссии платёжного канала не входят в эти 150 RUB.
Кнопка «Оплатить» открывает https://choco.tips/qr/50156198 во внешнем браузере только после создания заказа.
На странице пользователь вводит свой логин в поле «Имя». Автоматического эквайринга, webhook и автосписаний нет.
Поддержка Choco сообщила, что сервис предназначен для добровольных донатов и не разрешает оплату товаров/услуг;
переход по ссылке реализован по явному запросу владельца проекта и не означает одобрения сервиса.

## Привязка
ID аккаунта приложения должен **точно совпадать с email клиента 3x-ui** (с учётом регистра).
subId не используется для поиска и может отличаться. После поиска по email сервер берёт subId
из записи клиента и использует его для чтения конфигураций через SUBSCRIPTION_BASE.
Это одновременно исправляет загрузку подписки при различающихся email и subId.

Адаптер реализован для **3x-ui v3.11.0**:
- GET panel/api/clients/get/{email}
- POST panel/api/clients/update/{email}
- Authorization: Bearer (API token с admin-доступом)

Контракт проверен по исходникам и OpenAPI этой версии:
https://github.com/MHSanaei/3x-ui/blob/v3.11.0/docs/public/openapi.json
https://github.com/MHSanaei/3x-ui/blob/v3.11.0/internal/web/controller/client.go

В этой версии email идентифицирует общую запись клиента. Обновление распространяется панелью
на связанные inbound, без фильтрации по subId. Удостовериться в одинаковом email на независимых
панелях недостаточно: текущая интеграция работает с **одной управляющей панелью** и её узлами.

## Как проходит оплата
1. В приложении пользователь открывает «Продлить подписку» и видит тариф и BILLING_INSTRUCTIONS.
2. Нажимает «Создать заказ»; сервер определяет аккаунт только по bearer-сессии.
3. После создания заказа приложение показывает логин аккаунта для поля «Имя» и кнопку «Оплатить».
   Пользователь открывает https://choco.tips/qr/50156198, вручную вводит логин в поле «Имя» и сумму 150 ₽.
   Логин, пароль и токены не добавляются к URL; предзаполнение полей стороннего сайта не предполагается.
4. После оплаты пользователь возвращается в приложение. Заказ остаётся pending; повторно оплачивать не нужно.
   Администратор открывает /billing и сверяет поступление, имя/логин, сумму и соответствующий заказ.
5. Нажимает «Проверить» у заказа, сверяет срок и подтверждает оплату кнопкой.
   Ввод номера операции, суммы и дополнительная галочка не требуются; сумма берётся из заказа.
   Имя отправителя само по себе не доказывает оплату. Переход/возврат браузера также не подтверждает платёж.
   Для applying/retry/paid кнопки повторной оплаты нет.
6. Сервер сохраняет целевой срок и отправляет обновление в 3x-ui. Пользователь нажимает
   «Проверить статус»; после подтверждения приложение запрашивает обновление подписки.

Сумма хранится целым числом в копейках. Цена и период задаются сервером; поля account/amount из
пользовательского запроса не определяют владельца или цену. Пользователь не может подтверждать оплату.
Заказ можно создать и из админки для уже активированного аккаунта.

## Настройка на сервере
В существующий /etc/tngl-auth.env добавьте переменные (не заменяйте файл целиком):
- XUI_URL: адрес панели с её базовым путём и завершающим /, без panel/api.
- XUI_API_TOKEN: серверный API token панели. Не передавайте в APK, GitHub, URL или журналы.
- BILLING_DB=/var/lib/tngl-auth/billing.sqlite
- BILLING_INSTRUCTIONS: инструкция создать заказ, нажать «Оплатить», указать логин в поле «Имя» на Choco,
  затем вернуться и дождаться ручной проверки. Точный логин приложение показывает из серверного заказа.
  Максимум 1000 символов, обычный текст, не HTML. Для EnvironmentFile используйте одну строку в кавычках.

Пример структуры без настоящих секретов есть в .env.example.
HTTPS проверяется штатным хранилищем сертификатов. HTTP разрешён только для loopback.
При отсутствии настроек оплаты /v1/billing возвращает billing_unavailable. До настройки
клиент не создаёт заказы и показывает соответствующее сообщение.
Для включения поиска по email достаточно XUI_URL + XUI_API_TOKEN; сам биллинг дополнительно требует BILLING_INSTRUCTIONS.

Перед обновлением остановите tngl-auth и tngl-admin и сохраните резервную копию auth.sqlite вместе с WAL,
если он есть. Для существующего billing.sqlite также сохраняйте резервную копию с WAL.
Используйте SQLite backup либо копирование при остановленных сервисах. Не переносите тестовые базы в production.

Перенесите обновлённые server/*.mjs и package.json в /opt/tngl-auth, сохранив /etc/tngl-auth.env
и /var/lib/tngl-auth. Не перезаписывайте существующий env примером.
В установленном nginx-admin.conf увеличьте proxy_read_timeout до 90s (в репозитории уже исправлено).
После nginx -t перезагрузите Nginx и перезапустите оба сервиса. Процессам нужен доступ к одному BILLING_DB.
До реального подтверждения проверьте preview заказа: он показывает email, число подключений,
текущий и целевой срок без изменения подписки.

## Сроки, трафик и особые случаи
Целевой срок = max(текущий срок, время начала подтверждения) + 30 суток.
Трафик, квота, учёт использованного трафика, UUID, subId, аппаратные лимиты, группа и прочие
параметры клиента сохраняются. Запросы сброса трафика не выполняются.

Автоматическое подтверждение отклоняется для отключённого клиента, исчерпанной квоты,
бессрочного/отложенного срока (expiryTime <= 0), настроенного auto-renew reset/resetDay/resetWeekday.
Наличие WireGuard/AmneziaWG ключей и адресов не блокирует продление.
При запросе обновления адаптер НЕ передаёт privateKey, publicKey, preSharedKey, allowedIPs,
allowedIPsByInbound, keepAlive и forwardedPorts. В 3x-ui 3.11.0 UpdateInboundClient сохраняет эти
поля из каждого существующего peer; таким образом общий ClientRecord не перезаписывает разные
ключи/адреса нескольких туннелей. Внутреннее представление allowedIPs в записи может быть CSV:
оно не отправляется в поле API, требующее массива, и не преобразуется с потерей данных.
Остальные настройки клиента передаются как прежде с новым абсолютным сроком.
Это поведение привязано к 3.11.0; после обновления панели сверяйте контракт и тесты.
Источник: https://github.com/MHSanaei/3x-ui/blob/v3.11.0/internal/web/service/client_inbound_apply.go#L767

Для старого retry-заказа с tunnel_client_requires_review после установки исправления повторите
подтверждение того же заказа, если платёж проверен. Сброс не требуется: сохранённый абсолютный срок
защищает от повторного начисления. Администратор должен сначала согласовать подходящий тариф/
настройки с владельцем; не подтверждайте оплату, если preview сообщает ошибку.

Подтверждение меняет только срок. Оно не снимает ограничения группы/inbound и не увеличивает трафик.
Неполадки/лимиты самих узлов проверяются в 3x-ui. При pendingSync панель приняла обновление,
но на момент подтверждения некоторые узлы ожидали синхронизации. Этот флаг — запись результата
подтверждения, а не непрерывный мониторинг узлов. Проверьте узлы в панели; при необходимости обновите
подписку в приложении после синхронизации.

С настроенным XUI вход проверяет пароль аккаунта и существование соответствующего клиента, но
не требует действующей VPN-конфигурации. Так пользователь с истёкшей подпиской может войти для продления.
Старый режим без XUI сохраняет прежнюю проверку активной подписки.
Сбои загрузки конфигурации после успешной авторизации не превращаются в ошибку пароля на Android.

## Защита от повторов и ограничения согласованности
- Один незавершённый заказ на аккаунт; повторное создание возвращает тот же заказ.
- Внешний номер платежа не вводится. Сервер сохраняет внутренний идентификатор manual:<номер заказа>;
  старые reference остаются совместимыми. Это не позволяет автоматически распознать один платёж,
  ошибочно зачтённый разным заказам: администратор самостоятельно сверяет поступления.
- Цена заказа сохраняется при создании и не задаётся формой подтверждения.
- До удалённого изменения сохраняются ID клиента, исходная и целевая дата.
- После тайм-аута/перезапуска повтор подтверждения того же заказа отправляет тот же абсолютный срок.
  Повтор уже подтверждённого заказа возвращает его результат без повторного начисления.
- Параллельное подтверждение блокируется памятью процесса и краткой SQLite lease.
  После аварии дождитесь 60 секунд и повторите подтверждение того же заказа.
- Если email теперь указывает на другую запись или срок изменён вне этой операции,
  автоматическое продолжение блокируется: panel_client_changed. Сверьте историю с панелью.
- 3x-ui может применить обновление частично и вернуть success:false. Заказ остаётся retry,
  а повтор восстанавливает тот же срок. Не создавайте второй заказ и не учитывайте платёж повторно.
- Нет общей транзакции между SQLite и 3x-ui и нет compare-and-swap в этом API.
  Во время подтверждения не меняйте того же клиента вручную/другим биллингом.
  Используйте один экземпляр tngl-admin и одну общую базу BILLING_DB.
- Возвраты, оспаривания и исправления операторских ошибок не автоматизированы.
- Права admin и CSRF требуются для всех изменений в админке. Клиентские статусы — только для владельца сессии.
- В базе платежей нет API-токенов, паролей и VPN-конфигураций.

## Сброс заказа в админке
Кнопка «Сбросить заказ» у незавершённого заказа возвращает его в pending с прежним ID и ценой.
Срок подписки не меняется. После сброса пользователь нажимает «Проверить статус» в приложении;
снова доступна кнопка «Оплатить». Не просите оплачивать повторно уже поступивший платёж.

Сброс очищает ошибку и сохранённую попытку подтверждения, но сохраняет её снимок в
billing_order_resets. История заказов и платежей не удаляется.
Подтверждённый paid-заказ не сбрасывается. Текущая обработка блокирует сброс.
Если сохранён целевой срок, сервер сначала проверяет прежний ID клиента и исходный срок в 3x-ui.
Если срок или клиент уже изменился (в том числе после тайм-аута, когда продление фактически применено),
сброс отклоняется с order_reset_requires_review. Нельзя стирать исходную попытку и начислять дни заново;
проверьте панель и при необходимости повторите подтверждение исходного заказа.

API админки (Basic + CSRF):
POST /api/billing/confirm — {orderId}; все значения берутся из сохранённого заказа.
POST /api/billing/reset — {orderId}; не изменяет 3x-ui.

## API приложения
GET /v1/billing — {plan, instructions, order}; bearer-сессия.
POST /v1/billing/orders — {planId:"month30"}; bearer-сессия.
Для проверки состояния повторите GET /v1/billing.
