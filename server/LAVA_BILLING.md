# Продление через lava.top

Актуальная интеграция (15 ноября 2026); заменяет описание ручной оплаты Choco в BILLING.md.

Продукт TangledLink Pro: 0cee2edb-1432-4c9a-a239-592d51538413. Получен через авторизованный GET /api/v2/products.
Разовые тарифы: month30 — 150 RUB / 30 суток; month90 — 450 RUB / 90 суток;
month180 — 900 RUB / 180 суток; month360 — 1800 RUB / 360 суток. Не календарные месяцы.
Автосписаний нет (ONE_TIME). Цены и offerId зафиксированы на сервере в lava.mjs.
Новые счета создаются через PAY2ME с paymentMethod=SBP: Система быстрых платежей.
Не полагайтесь на значения по умолчанию — иначе lava.top предлагает карту.

migrate-lava-sbp.mjs создаёт новую ссылку СБП для старого pending-заказа при NEW/IN_PROGRESS/FAILED.
Открытая карточная форма тоже имеет статус IN_PROGRESS. COMPLETED не заменяется. Старые invoice_id сохраняются в lava_previous_invoices
и продолжают проверяться: поздняя оплата по старой карточной ссылке относится к тому же заказу
и не начисляет срок повторно. Старые ссылки не отменены на стороне Lava; не оплачивайте обе.
Два платежа за один заказ требуют ручной сверки/возврата второго, второй срок не начисляется.
При неоднозначном создании нового счёта устанавливается review, автоматического повторного создания нет.
Ожидание создания PAY2ME-счёта — до 30 секунд (раньше 7 секунд).
recover-lava-sbp.mjs сверяет недавние счета по точному email, продукту, сумме/валюте и исключает уже известные ID.
Только единственный кандидат может быть восстановлен; GET /api/v1/invoice может не вернуть paymentUrl.
В таком случае найденный ID сохраняется для сверки, и оператор отдельно создаёт новую ссылку.
В production текущий заказ переведён на СБП; все прежние ID сохранены. Оплаты скрипты не выполняют.

## Настройка
Только в /etc/tngl-auth.env: LAVA_API_KEY и отдельный LAVA_WEBHOOK_SECRET (32–80 символов).
Остаются обязательными настройки XUI_URL, XUI_API_TOKEN, BILLING_DB и BILLING_INSTRUCTIONS.
При включённой Lava старый текст инструкции не используется.
Webhook: https://auth.tngl.pro:8443/v1/billing/webhooks/lava, событие «Успешная оплата»,
аутентификация «API key вашего сервиса», значение LAVA_WEBHOOK_SECRET.
Порт 8443 обязателен: на 443 этого сервиса нет. Не отключайте проверку сертификата.
Webhook проверяется constant-time сравнением X-Api-Key. Неизвестные события отвечают 200,
запрос без ключа — 401. Размер JSON ограничен 8 KiB. Секретов в APK нет.

POST /v1/billing/orders: bearer-сессия, {planId,email}. Настоящий email нужен lava.top,
он не заменяет ID аккаунта VPN. Создаётся локальный заказ и POST /api/v3/invoice.
GET /v1/billing возвращает plans, instructions и order с paymentUrl.
На клиенте срок выбирается на странице подписки; затем вводится только email и нажимается «Оплатить».
После создания заказа браузер открывается автоматически. Возврат браузера не подтверждает оплату.

## Возврат в приложение
Новые счета содержат successful_return_url, failure_return_url и cancel_return_url:
https://app.tngl.pro/billing/return. На сайте размещены assetlinks.json с отпечатками release
и текущей локальной debug-подписи, а также статическая fallback-страница с кнопкой открытия pro.tngl.
Файл подтверждения выдаётся через HTTPS 443 без перенаправления. Manifest ограничен точным путём.
Debug-подпись относится только к текущему локальному ключу; при смене ключа обновите файл подтверждения.
При распространении через Google Play сверяйте отпечаток App Signing, а не только upload key.

MainActivity проверяет action, схему, host, порт и rawPath в onCreate и onNewIntent.
Параметры status/invoiceId и extras не определяют аккаунт и не меняют платёж/подписку.
Открывается вкладка подписки, выполняется GET /v1/billing по текущей сессии с коротким ограниченным повтором.
При отсутствии сессии сначала требуется вход. Возврат не создаёт заказ и не открывает оплату повторно.
Если браузер блокирует автоматический переход, на странице есть кнопка «Открыть TangledLink».

Нужно установить новую версию APK с intent-filter. Уже созданные Lava-счета сохраняют прежние
параметры возврата; интеграция применяется при создании новых счетов. Счета ради теста не перевыставлялись.
Скрипты/конфигурация сайта находятся в server/app-links/. Backups сайта и API сохранены на серверах.
Старые pending-заказы без счёта можно использовать для month30, введя email.
Заказ другого срока требует проверки, его цена не меняется задним числом.

## Проверка платежа и восстановление
Инвойс связан с аккаунтом только через локальный order_id → invoice_id.
Ни email, ни логин из webhook не выбирают VPN-аккаунт.
Перед продлением сервер сверяет GET /api/v1/invoices/{id}: ID, COMPLETED,
ONE_TIME, полную сумму RUB и email сохранённого счёта.
Постоянная таблица lava_invoices переживает перезапуск; worker раз в 5 секунд
обрабатывает до 20 инвойсов, выбирая давно проверенные. Состояние проверяется и при потере webhook.
Новый запрос создания возвращает прежнюю ссылку, не создаёт второй счёт.
Если создание счёта завершилось неоднозначно, состояние review блокирует повторное создание.
Требуется сверка оператором с историей Lava; не удаляйте эту запись автоматически.

Подтверждение использует существующий абсолютный target_expiry и SQLite lease биллинга.
При тайм-ауте 3x-ui повтор отправляет тот же срок, а не начисляет дни заново.
Ручные confirm/reset в админке запрещены для связанных с Lava заказов.
Старые ручные заказы остаются совместимыми. Админка показывает провайдера и фактическую сумму.
Ошибки проверки/продления видны в списке заказов; нельзя создавать второй заказ ради повтора.
Нет распределённой транзакции с 3x-ui: ограничения и проверки BILLING.md сохраняются.

## Ограничения
Реальная покупка и доставка события именно из кабинета Lava ещё должны быть проверены владельцем.
Завершённый live-платёж без действий пользователя не создавался.
Возвраты/чарджбэки и споры обрабатываются администратором, не отзывают срок автоматически.
Не включайте рекуррентные платежи: текущий поток рассчитан на разовые покупки.
При изменении цен в кабинете необходимо изменить серверные тарифы; несовпадение блокирует выдачу доступа.
Незавершённый инвойс не отменяется автоматически; неоднозначные счета требуют сверки.
База содержит email для сверки: ограничьте доступ и срок хранения в соответствии с политикой сервиса.
