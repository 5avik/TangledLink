# Registration and first subscription

Public registration is enabled only when REGISTRATION_TEMPLATE_EMAIL and REGISTRATION_INBOUND_IDS are configured alongside XUI_URL/XUI_API_TOKEN. Verified production configuration: template svk, inbound IDs 2,3,4,12,13,14,24,25,26,32 (UK/NL/RO TCP/gRPC/XHTTP and automatic selection). Additional template attachments are excluded. Only totalGB, limitIp, limitHwid are copied; credentials, subId, UUID, comments, reset schedules and other fields are never copied. Template limits are currently zero/unlimited.

POST /v1/register accepts id/password; new IDs use lowercase ASCII letters, digits, underscore and hyphen, length 3–32. Password length 12–128. The login is the panel email; receipt email remains independent. API credentials stay server-side. Existing local accounts, including invitation reservations and case variants, and existing panel identities cannot be claimed. Registration is limited to 5 attempts per IP per 15 minutes, in addition to existing limits. No email confirmation: one person can create multiple accounts; a trial is once per account, not once per person.

3x-ui 3.11.0 rejects add with zero inbounds. The adapter creates an independently keyed disabled client with expiryTime=1 on the first configured standard inbound, then detaches it. Success is returned only after verifying no inbound attachments. This is a temporary disabled bootstrap attachment, not a VPN trial. The API constraint is documented in upstream internal/web/service/client_crud.go Create. No panel database writes or panel source changes are used.

The existing auth SQLite database stores hashed credentials, registration UUID/subId and ready flag. Pending registration cannot log in or obtain a session. A retry with the same credentials continues the same identity. Different credentials cannot take it over. Membership records retain the panel numeric identity, independent credentials, trial absolute target, completed marker and paid intent. They share the existing AUTH_DB file; no DataStore or new database service.

GET /v1/account requires a session. Managed accounts expose subscribed/trialAvailable; legacy accounts retain their existing renewal behavior. POST /v1/trial requires a session, records one absolute expiry 30 days from the first request and issues only the configured inbound set. A network timeout retries the same target. A completed trial or first confirmed paid intent cannot start a new trial. Account-level SQLite leases serialize trial and paid grants across backend/admin processes. Payment confirmation prepares the account before recording its absolute billing target. First paid orders attach the same inbounds; subsequent paid periods preserve the legacy billing calculations and provider verification.

GET /v1/subscription denies a managed dormant/expired/disabled account before reading configs. The app displays the no-subscription card on the server picker, with trial, buy and refresh actions. Registration and trial use MainAction/MainViewModel, never Canvas or a service callback. Account-status requests capture their session token so an old account's response cannot change a newly signed-in account's status.

Back up AUTH_DB (including registration/membership tables) as a consistent SQLite snapshot. Never clear membership/trial markers to reset a password. Password reset/revocation continues through existing admin actions. New schema creation is additive. Keep backup env and SQLite files protected.
